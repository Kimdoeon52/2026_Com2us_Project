### 요약
KKH(전투 데이터/DB 담당)가 먼저 만들어둔 `CombatDataHub` 연동 지점을 확인하고, 판정(히트박스/허트박스/푸시박스) 시스템의 기초를 처음부터 구현했다. 그 과정에서 "대기 중엔 맞을 수도 없는" 구멍과 "가드가 프레임 모델에 안 맞는" 구조적 문제를 발견해서 설계를 바꿨다.

### 한 일

- **`fighterId` 배선**: `ActionExecutor`에 `FighterId` 프로퍼티 추가, `PlayerRobotBootstrap`에서 인스펙터로 `"Player"`/`"Enemy"` 지정. KKH의 `CombatDataHub` API가 전부 문자열 ID로 로봇을 구분하기 때문에 필요했음.
- **KKH 데이터 구조 파악**: `PartMasterData`/`CoreMasterData`(원장 SO), `CombatantSnapshot`(런타임 상태), `CombatCalculator`(순수 계산), `CombatDataHub`(API 창구), `BattleManager`(라이프사이클). NYH의 `BodyPart` enum과 `ActionData` 필드(`Damage`, `IsGuardable`, `StaggerValue` 등)를 KKH 쪽이 이미 계약으로 삼아 코드를 짜놨다는 걸 확인함 — 필드명을 함부로 바꾸면 KKH 쪽이 깨짐.
- **`FrameBox` 판정 데이터 구조**: `BoxType`(Hit/Hurt/Push) enum, `FrameBox` struct(부위·좌표·활성 프레임 구간), `ActionData.GetActiveBoxes(globalFrame)`, `ActionState.GlobalFrame`(행동 전체 타임라인 기준 경과 프레임).
- **`BoxResolver`**: 로컬 좌표 → 월드 좌표 변환(좌우 반전 포함)을 하는 단일 지점. `BoxDrawer`와 나중에 만들 `HitDetection`이 둘 다 이 함수 하나만 쓰게 만듦 — 여러 곳에 변환 로직을 흩어두면 반드시 한쪽에서 반전을 빠뜨리기 때문.
- **`BoxDrawer`**: Scene 뷰에 `OnDrawGizmos`로 판정 박스를 그리는 디버그 도구.
- **`FrameStepper`**: F2(정지)/F3(1프레임 전진) 디버그 도구.
- **`ActionDataEditor`**: `ActionData` 에셋을 Scene 뷰에서 마우스로 드래그해 박스를 맞추는 커스텀 에디터. 원래 계획엔 없었는데, 숫자를 직접 타이핑하는 게 너무 느려서 추가로 만듦.
- **대기/이동 중 박스 처리**: `ActionState.IdleAction` + `GetActiveBoxes()` 통합, `Idle.asset` 신규 제작(Hurt+Push만, Hit 없음).
- **가드 판정 재설계**: 버튼(C키) 방식에서 "상대를 바라보는 방향의 반대쪽을 누르면 자동 가드"(SF2 방식)로 변경. `ActionExecutor.IsGuarding`이 매 틱 계산.
- **위닝 무적 플래그 수정**: `Weaving.asset`의 `isInvincibleDuringActive`가 꺼져 있던 걸 프레임표 기준(6프레임 무적)으로 켬.
- **`CLAUDE_1.md` 갱신**: 위 변경사항 전부 반영 (§4, §5, §8, §9, §11, §14 추가).

### 문제 → 원인 → 해결

**1. F3로 프레임을 넘겨도 애니메이션이 안 움직임**
- 증상: F2로 정지 후 F3를 여러 번 눌러도 캐릭터가 가만히 있다가, 한참 뒤에 갑자기 대기 자세로 툭 튀었다.
- 원인: `Animator`는 `Update()`의 `Time.deltaTime`으로만 재생되는데, `Time.timeScale = 0`이면 `Time.deltaTime`도 0이라 자동으로는 전혀 진행하지 않는다. F3는 `CombatClock.Tick()`만 수동 호출했는데, 이건 논리(`ActionState`)만 전진시킬 뿐 `Animator`엔 아무 영향이 없었다. 그래서 논리적으로는 Recovery까지 다 끝났는데 그림은 처음 그대로 있다가, `OnActionEnd`가 발동해 `animator.Play(idle)`을 부르는 순간 화면이 툭 튀어 보인 것.
- 해결: `RobotView.AdvanceOneTick()`을 추가해서 `animator.Update(CombatClock.TICK)`으로 애니메이터를 수동으로 1틱만큼 밀 수 있게 만들고, `FrameStepper`의 F3 처리에서 `CombatClock.Tick()` 직후에 씬의 모든 `RobotView`에 대해 이 메서드를 호출하도록 함.

**2. `ActionDataEditor`로 박스를 추가했는데 Scene 뷰에 아무것도 안 보임**
- 증상: 인스펙터에 `Frame Boxes` 값(Rect 0,0,0.3,0.3 등)은 제대로 들어갔는데 Scene 뷰에 박스가 전혀 안 그려짐.
- 원인: Unity `Handles`는 기본적으로 depth test(zTest)가 걸려 있어서, 바닥(`Ground`)이나 캐릭터 스프라이트 쿼드 같은 3D 지오메트리 뒤에 있으면 그려놓고도 가려진다. 박스가 캐릭터 발밑(피벗) 바로 근처에 그려지다 보니 이 문제에 정확히 걸렸다.
- 해결: `OnSceneGUI`에서 `Handles.zTest = CompareFunction.Always`로 강제해서 항상 맨 위에 그려지게 함. 진단용으로 기준 위치를 보여주는 노란 십자 마커도 같이 추가.

**3. 대기·이동 중엔 허트박스/푸시박스가 아예 없었음**
- 증상(발견 계기): "걸을 때는 판정이 어떻게 되냐"는 질문을 받고 코드를 다시 보니, `FrameBox`가 `ActionData`에만 있고 걷기/대기는 `ActionState.CurrentAction`이 계속 `null`이라 아무 박스도 없다는 걸 확인함. 즉 서 있는 상대를 때려도 맞은 판정 자체가 안 뜨고, 로봇끼리 서로 뚫고 지나갈 수 있는 상태였음.
- 원인: 걷기/대기는 3구간(선딜→활성→후딜) 상태기계를 거치지 않게 설계했는데, "행동 중이 아닐 때의 몸통 판정"을 어디서 가져올지를 놓쳤음.
- 해결: `ActionState`에 `IdleAction` 참조를 추가하고, `GetActiveBoxes()`가 `CurrentAction`이 없으면 `IdleAction`의 박스를 대신 반환하도록 통합. `Idle.asset`(Hit 없이 Hurt+Push만)을 새로 만듦.

**4. `Guard.asset`의 프레임 값이 구조랑 안 맞음**
- 증상: 프레임표엔 가드가 "선딜 2 / 활성 **유지** / 후딜 10"인데, `ActionData.ActiveFrames`는 고정된 정수라서 "유지"(키를 누르고 있는 동안 계속)를 표현할 방법이 없었음. 실제로 `Guard.asset`엔 `activeFrames: 0`으로 들어가 있어서, 지금 구조 그대로면 가드가 사실상 즉시 후딜로 넘어가 버려 전혀 안 막아주는 상태였음.
- 원인: 3구간 상태기계는 "고정된 프레임 수"를 전제로 설계됐는데, 가드는 애초에 그 전제에 안 맞는 행동(입력이 지속되는 동안 유지)이었음.
- 해결: 가드를 `ActionData`/`ActionState` 밖으로 완전히 빼서, 매 틱 "상대를 바라보는 방향의 반대쪽을 누르고 있는가"로 직접 계산하는 방식(SF2 방식)으로 재설계. `ActionExecutor.IsGuarding` 추가. `Guard.asset`은 실행 경로에서 더는 안 쓰임.

### 설계 결정과 이유

- **박스 프레임 기준을 `GlobalFrame`(행동 전체 타임라인, Phase 안 가리고 누적)으로 통일**: 허트박스는 선딜·활성·회수 내내 존재해야 하는데, `FrameInPhase`는 Phase가 바뀔 때마다 0으로 리셋되어 "지금이 전체 중 몇 번째 프레임인지"를 알 수 없었다. 별도 누적 카운터를 추가해서 해결.
- **위닝 무적을 액션 이름이 아니라 `IsInvincibleDuringActive` 플래그로 판정**: `if (action.ActionName == "위닝")` 같은 분기를 CLAUDE.md §13이 명시적으로 금지하고 있어서, 대신 "지금 무적 플래그가 켜진 행동의 활성 구간인가"만 본다. 나중에 다른 무적기가 생겨도 코드 수정이 필요 없다.
- **가드도 같은 원칙으로, 액션이 아니라 매 틱 계산되는 상태로 뺐다**: 처음엔 `Guard.asset`에 `isGuardStance` 같은 플래그를 추가하는 것도 고려했지만, 근본 문제(고정 프레임 vs 유지)가 안 풀려서 아예 판정 방식 자체를 바꿈.

### 다음에 할 일

1. `HitDetection` — AABB 겹침 판정. 선행 조건(`FrameBox`, `GetActiveBoxes`, `IsGuarding`, `IsInvincibleDuringActive`)은 이제 다 준비됨.
2. `CombatDataHub.CanExecuteAction` 게이트 — 지금은 부위가 파손돼도 기술이 그냥 나감.
3. 가드 애니메이션 훅 — `IsGuarding`은 `ActionState`를 안 거치니까 `RobotView`의 기존 이벤트 구독 방식으로는 애니메이션이 안 걸림. 별도로 연결 필요.
4. `PlayerInputSource`의 C키(가드) 매핑 정리 — 이제 안 쓰이는 죽은 코드.
5. `RobotAssembler` — 실제 장착 파츠로 `CombatantSnapshot`을 조립해서 `BattleManager.InitializeBattle`에 등록하는 코드. 지금은 테스터의 더미 데이터로만 검증됨.

### 한 일

- **`DummyJabInputSource`(임시)**: `IInputSource` 구현체. Idle이 될 때마다 인스펙터에 넣은 잽을 돌려줘서 잽을 계속 반복한다. 이동 없음. 대기 틱 수는 인스펙터 값(기본 0 = 연타). 정식 `AIInputSource`가 나오면 삭제.
- **`PlayerRobotBootstrap` 수정**: 입력원을 `PlayerInputSource`가 아니라 `IInputSource`로 찾게 변경. `RobotMover`가 없으면 예외 대신 경고만 남기게 변경.
- **Walk/BackWalk 전환**: `RobotView`가 매 렌더 프레임 이동 입력과 `RobotMover.FacingRight`를 비교해서, 상대 쪽으로 누르면 `Walk`, 반대쪽이면 `BackWalk`, 입력 없으면 `Idle`을 `Play()`로 직접 재생. 같은 스테이트는 다시 Play하지 않음(클립 되감김 방지). 행동 중엔 건드리지 않음.

### 문제 → 원인 → 해결

**1. 적에게 행동을 넣어도 판정 박스가 안 보임**
- 증상: Enemy 오브젝트의 박스가 Scene 뷰에 전혀 안 그려짐.
- 원인: Enemy에 `RobotMover`가 없어서 `PlayerRobotBootstrap.Awake`의 `mover.Init(...)`에서 NullReferenceException → 그 뒤의 `BoxDrawer.Init`/`RobotView.Init`이 실행되지 않음. 또 방향을 모르니 적 박스가 항상 오른쪽 기준으로 계산됨.
- 해결: 부트스트랩에 null 방어 추가 + Enemy에 `RobotMover`(opponent = Player)를 붙이도록 씬 수정.

**2. 적에게 입력을 줄 방법이 없음**
- 원인: 부트스트랩이 `GetComponent<PlayerInputSource>()`로 구체 타입을 찾고 있어서, 다른 입력원을 붙여도 인식을 못 함. §8("입력만 바꿔 끼운다") 취지와 어긋나 있었음.
- 해결: `GetComponent<IInputSource>()`로 변경.

### 설계 결정과 이유

- **걷기 전환을 Animator 전이 조건이 아니라 코드의 `Play()`로**: §2 규칙. 컨트롤러의 Idle↔Walk 전이 선은 조건도 Exit Time도 없어서 원래부터 무시되고 있었음(이동 중 Walk가 안 나오던 이유).
- **앞/뒤 걷기 기준은 "거리 변화"가 아니라 "바라보는 방향 대비 입력 방향"**: 로봇은 항상 상대를 바라보므로 둘은 같은 뜻이고, 방향 비교가 가드 판정(`IsGuarding`)과 같은 기준이라 일관됨.

## 2026-09-28

### 요약
"선딜을 줄이거나 판정을 늘리는 기술이 나중에 들어올 텐데 지금 구조로 되냐"는 질문에서 출발해서,
`FrameBox`가 절대 프레임을 들고 있는 게 근본 문제라는 걸 확인하고 구간 앵커 + `ResolvedAction`으로 바꿨다.
바꾸는 과정에서 기존 에셋에 이미 들어있던 판정 버그 3개를 발견했다.

### 한 일

- **`FrameAnchor` enum + `FrameBox` 앵커 필드**: `anchor` / `startOffset` / `length` 추가.
  `Legacy`(기본값 0)면 예전처럼 `startFrame/endFrame`을 그대로 써서, 필드만 추가한 시점에도 동작이 안 바뀐다.
- **`ResolvedAction`(2층)**: `ActionData` + `FrameAdjustment` → 이번 실행분의 확정 프레임·절대 박스 창.
  `ActionState.Begin()`에서 1회 계산.
- **`FrameAdjustment`(2층)**: 선딜/활성/후딜 가감 + 전체 속도 배율. 지금은 전부 0(보정 없음).
- **`ActionState`**: `Timeline` 프로퍼티 추가. `Advance()`의 Phase 전환과 `GetActiveBoxes()`가
  원본 SO 대신 확정값을 본다. 보정을 옮겨 담는 자리는 `BuildAdjustment()` 하나.
- **`RobotView`**: `animator.speed` 계산의 데이터 길이를 원본 `TotalFrames`에서 `Timeline.TotalFrames`로.
- **`ActionExecutor`**: 행동 시작 로그를 확정값 기준으로.
- **`ActionDataEditor`**: "절대 프레임 → 앵커 변환" 버튼 + 검수 경고 패널.

### 문제 → 원인 → 해결

**1. 프레임을 바꾸는 기술을 만들 방법이 아예 없었음**
- 증상: "선딜 2프레임 단축" 장비를 만들려고 보니 넣을 자리가 없었다.
- 원인: `ActionState.Advance()`가 `CurrentAction.StartupFrames`를 SO에서 직접 읽는다. 바꾸려면
  ① SO 런타임 수정(§2 위반) ② 기술 이름 분기(§13 위반) ③ 변형 에셋 복제(박스 좌표가 에셋마다 중복)
  셋뿐인데 전부 막혀 있다. 상희 님의 `ResolvedModifiers`는 히트박스 크기까지만 손댈 수 있었다.
- 해결: `ActionData`(불변) + `FrameAdjustment`(보정) → `ResolvedAction`(확정)으로 확정 지점을 한 곳에 만들었다.
  원본은 한 번도 안 바뀌고, 확정이 `Begin()` 한 곳에서만 일어나니 기술이 몇 개로 늘어도 이 자리는 하나다.

**2. 박스 크기 보정과 프레임 보정을 같이 쓰면 깨지는 구조였음**
- 증상(발견 계기): 크기 보정은 이미 되는데 프레임 보정을 얹으면 어떻게 되냐를 따져보다 발견.
- 원인: 박스 창이 절대 프레임이라 프레임이 줄어도 안 따라온다. 커진 히트박스가 엉뚱한 프레임에 켜진다.
- 해결: 박스가 구간을 가리키게 하고(앵커), 확정 프레임에서 창을 계산한다. 프레임과 박스가 같은 자리에서
  같이 정해지므로 둘이 어긋날 수가 없다. §4의 "표시기가 별도 데이터를 보면 거짓말하는 표시기가 된다"와 같은 원칙.

- `Hook`: Hurt박스 하나의 `rect.width`가 **-0.38(음수)**. 폭이 음수면 `xMin > xMax`라 AABB 겹침이
  항상 false다 — 그 허트박스는 아무 기능도 안 하고 있었다. Scene 뷰에서 드래그하다 뒤집힌 듯.
- 전부 **에러가 안 나고 게임도 돌아가는** 종류라 눈으로는 못 찾는다. 그래서 `ActionDataEditor`에

- 대신 csproj를 임시로 복사해서 새 파일을 넣고 `dotnet build`로 확인했다. DOTween을 쓰는 LJS·LSH 파일이 참조 해석에 실패해서
  나머지 파일의 본문 검사까지 멈추는 바람에(일부러 넣은 오류도 안 잡힘) 그 두 폴더를 빼고 다시 돌렸다. NYH 쪽 오류 0건.

### 설계 결정과 이유

- **AI에 상태기계를 두지 않았다**: "공격 중/경직 중/공중/사망"은 이미 `ActionState`·`RobotMover`에 있다. AI가 같은 걸 또 들고
  있으면 둘이 어긋나는 순간 버그가 된다. AI는 "Idle일 때 다음에 뭘 할지"만 고른다.
- **Behavior Tree 대신 가중치 선택 + SO**: 기술 4개에는 BT가 과하고, 몹이 늘어도 클래스는 그대로 두고 프로필 에셋만 늘리면 된다(§1).
- **경직을 상태값이 아니라 "피격 행동"으로 만들었다**: 경직 길이·박스·애니메이션이 에셋 하나에서 나오고, 상태기계에 새 Phase가 필요 없다.
  공중·사망만 예외로 막으면 나머지는 기존 3구간 흐름을 그대로 탄다.
- **투사체 데미지를 쏜 ActionData에서 가져온다**: KKH `ProcessHit`이 ActionData를 받는 계약이라, 데미지 출처를 둘로 나누지 않았다.
- **총알이 회피 무적에 닿으면 "통과"**: 근접처럼 `isWeaving=true`로 넘기면 겹치는 매 틱마다 회피 판정이 나고 총알도 터진다.
- **사망 감지는 HP를 매 틱 직접 본다**: 데미지가 들어오는 길(근접·총알·나중의 기믹)이 여러 갈래라, 피격 지점에서만 확인하면 빠뜨린다.
- **사망 후 오브젝트를 끄지 않고 스프라이트만 끈다**: HitDetection·KKH BattleManager가 계속 참조하고 있어서 비활성화하면 구독 해제 순서까지 챙겨야 한다.

2. 실제 플레이로 확인: 기술 4종이 다 나오는지, 총알이 플레이어에 맞고 터지는지, 경직·점멸·띄우기·사망 연출.

### 같은 날 이어서 — "공격 안 하고 점프만 함" + 착지 모션 안 나옴

**1. AI가 공격을 안 하고 대기·점프만 반복**
- 원인: 적 `ActionExecutor.allActions`에 빈 칸 하나만 들어 있었다. `RuntimeRobot.IsAvailable`은 등록된 기술만 통과시키므로
  AI 후보에서 기술 4종이 전부 빠지고, 남은 선택지(대기·점프)만 뽑혔다. 에러가 안 나서 원인을 알기 어려운 종류.
- 해결: 인스펙터 연결 + `AIInputSource.Start`에서 "프로필 기술이 allActions에 없으면" 경고 로그를 띄우게 했다.

**2. 새로 만든 착지 모션(`Enemy1_Emergency_Disengagement_2_to_land`)이 안 나옴**
- 원인: 착지를 `RobotView`가 "점프 클립의 뒷부분(68.75%부터)"으로 그리게 해뒀다. 컨트롤러에서 Jump_Loop → to_land → Idle로
  이어도 코드가 `Play()`로 직접 고르기 때문에 그 전이는 안 탄다. to_land → Idle 전이(Exit Time 0.5)는 오히려 착지를 반쯤에서 잘라먹는다.
- 해결: 착지를 그림이 아니라 **행동**으로 바꿨다. `ActionExecutor.landAction`(`Enemy_Land.asset`, 0/0/30f, Hit박스 없음)을
  착지 순간 틱 안에서 시작한다 → 착지 동안 이동·공격이 멈춰서 "쿵 내려앉는" 묵직한 느낌이 난다. `RobotView`의 착지 칸 3개는 삭제.
  to_land → Idle 전이는 음소거.
- 설계 결정: 묵직함은 "그림이 얼마나 길게 나오나"가 아니라 "그동안 못 움직이나"에서 나온다 — 그래서 상태(ActionState)가 맡는 게 맞다.

### 같은 날 이어서 — 일시정지 중 박스 편집이 화면에 안 따라옴 + 밀림 값 정리

**1. F9로 멈추고 인스펙터에서 Hit박스 좌표를 바꿔도 빨간 박스가 안 움직임**
- 원인: 09-28 프레임 보정 작업 때 `ResolvedAction`이 `Begin()` 순간 박스 배열을 통째로 복사해 두게 바뀌었다.
  그 행동이 끝날 때까지는 복사본만 보니 SO를 고쳐도 반영이 안 됐다(09-21까지는 SO를 매번 직접 읽어서 됐던 것).
- 해결: 확정하는 건 프레임 3개(선딜·활성·후딜)만 남기고, 박스는 `GetActiveBoxes`가 부를 때마다 원본 SO에서 읽어
  창만 확정 프레임으로 계산하게 바꿨다. 박스 몇 개짜리라 매번 계산해도 비용 문제 없음.

**2. 밀림(knockbackDistance) 값을 지어서 넣었던 것 되돌림**
- 기획서1009 §6-12-10에 "피격시 약간의 밀려남"이라는 문장은 있지만 **거리 수치는 없다.** 0.15/0.3/0.1은 내가 지은 값이었다(§12 위반).
- 적 Skill1~4 전부 0으로 되돌림. 기획 수치가 나오면 에셋 값만 넣으면 `KnockbackSystem`이 그대로 동작한다.
