## 1. 왜 바꾸려 하는가

앞으로 **선딜이 줄거나 / 판정(활성 프레임·히트박스 크기)이 늘거나 / 전체 속도가 빨라지는** 장비·스킬이
들어올 가능성이 높다고 기획 쪽에서 확인됨. 지금 구조로는 이 중 **히트박스 크기 하나만** 가능하다.

### 지금 막혀 있는 지점

| | 현재 |
|---|---|
| 히트박스 크기 ± | ✅ 가능 (CSH `ResolvedModifiers.HitBoxWidthAdd/HeightAdd`) |
| 박스 위치 이동 | ❌ |
| 선딜 / 활성 / 후딜 프레임 ± | ❌ |
| 전체 속도 ± | ❌ |
| 박스가 켜지는 프레임 구간이 프레임 보정을 따라감 | ❌ |

`ActionState.Advance()`가 `CurrentAction.StartupFrames`를 **SO에서 직접** 읽고,
`FrameBox.startFrame/endFrame`이 **절대 프레임 숫자**라서 그렇다.

### 절대 프레임의 근본 문제

잽 에셋에는 "활성 구간이 언제인가"가 두 번 적혀 있다.

- 프레임 값: `4 / 2 / 6` → 활성은 5~6프레임
- 박스 창: `startFrame 5, endFrame 6`

두 번째는 첫 번째에서 손으로 계산해 옮긴 **사본**이다. 선딜을 4→3으로 바꾸면 박스 숫자도 같이 고쳐야 하고,
안 고쳐도 **컴파일 에러도 런타임 에러도 안 난다.** 조용히 틀어진다.

§4가 박스에 적용한 원칙("판정과 표시는 같은 데이터를 본다 — 표시기가 별도 데이터를 보면 거짓말하는
표시기가 된다")이 프레임 값에는 아직 적용되지 않은 상태다.

## 2. 바꿀 구조

### 두 층을 같은 타임라인 위에 겹친다

- **도트 층 (그림)** — `[스프라이트, 지속 프레임]` 목록. 각 도트에 **Hurt·Push 박스**
- **구간 층 (판정)** — `선딜 / 활성 / 후딜` 프레임 수. **Hit 박스**는 활성 구간에 앵커

§4의 "Hurt는 **도트 1장당** 1세트 / Hit는 **활성 구간당** 1개"를 그대로 데이터 구조로 옮긴 것이다.
팔을 뻗으면 맞는 범위가 같이 늘어나야 하니 Hurt는 그림을 따라가고,
판정은 프레임표가 진실이니 Hit는 구간을 따라간다.

**도트 경계와 구간 경계는 일치하지 않는다.** 잽에서 주먹 뻗은 도트는 4~7프레임인데 활성은 5~6프레임이다.
뻗은 그림이 판정보다 1프레임 먼저 나오고 1프레임 늦게 들어간다 — 정상이고, 그래야 자연스럽다.
그래서 "도트 = 구간"으로 묶지 않는다.

### ResolvedAction — 확정은 한 곳에서 한 번

```
ActionData(불변 SO)  +  ResolvedModifiers(CSH 보정)  →  ResolvedAction(이번 실행의 확정값)
```

`ActionState.Begin()`에서 1회 계산해서 확정 프레임 3개 + 절대 박스 창을 만든다.
`Advance()`와 `GetActiveBoxes()`는 SO가 아니라 이 확정값만 본다.
행동 도중에 프레임이 바뀌는 일이 없으므로 매 틱 재계산은 필요 없다.

이러면 §2(SO에 가변 상태 금지)와 §13(기술 이름 분기 금지)을 어기지 않고 보정을 넣을 수 있다.
지금 구조에서 선딜을 줄이려면 ① SO 런타임 수정(§2 위반) ② 기술 이름 분기(§13 위반)
③ 변형 에셋 복제(박스 좌표 중복) 셋뿐이라 사실상 길이 없다.

### 보정별 처리

| 보정 | 구간 층 | 도트 층 | 박스 |
|---|---|---|---|
| 선딜 -4 | 선딜 4→0 | 선딜에 걸친 도트 지속 0 → 준비 그림 안 나옴 | 자동 |
| 활성 +2 | 활성 2→4 | 활성에 걸친 도트가 2프레임 더 유지 | 자동 |
| 속도 +20% | 세 구간 전부 스케일 | 전체 비례 스케일 | 자동 |
| 히트박스 크기 ± | — | — | 지금 방식 유지 |

도트 층은 **구간이 바뀐 비율만큼 그 구간에 걸친 도트를 스케일하고 반올림**,
반올림 오차는 그 구간의 **마지막 도트가 흡수**한다.
(예: 잽 선딜 4→3 → 도트A 3f×0.75=2.25→2, 도트B의 선딜 몫 1f×0.75=0.75→1, 합 3 ✓)

## 4. 예상 문제와 차단책

### 🔴 데이터가 날아갈 수 있는 것

**P1. `FrameBox` 필드를 지우면 기존 `.asset` 값이 즉시 소실된다.**
Unity 직렬화는 필드가 사라지면 그 값을 버린다. 25개 박스를 다시 찍어야 한다.
→ **신규 필드 추가 → 변환 → 런타임 전환 → 구 필드 제거**의 4단계로만 진행 (§5 순서).
→ 변환 실행 전 반드시 커밋. 변환은 파괴적이고 Ctrl+Z로 다 안 돌아온다.

### 🟠 조용히 틀어지는 것 (에러가 안 남)

**P2. `animationClipName`은 클립 파일명이 아니라 Animator 스테이트 이름이다.**
에셋은 `Jap` / `Straight` / `Weaving`인데 실제 파일은 `Action_Jap` / `Action_Player_Straigt`(오타) /
`Action_Weacing`(오타)다. **이름으로 클립을 자동으로 못 찾는다.**
→ 변환 버튼에서 클립을 **직접 드래그해 넣게** 한다. 런타임 필드는 추가하지 않는다(에디터 전용).

**P3. 클립 키 개수 ≠ `TotalFrames`이면 도트 층이 통째로 어긋난다.**
지금은 5개 다 맞지만, 클립을 재수출하면 깨질 수 있다.
→ 변환 시 개수 불일치를 **경고로 띄우고 변환을 막는다.** 조용히 넘어가면 안 된다.

**P4. 샘플레이트가 클립마다 다르다 (60 / 12 혼재).**
훅·위닝은 20·37키가 1/12초 간격이라 클립 실제 길이가 프레임표의 5배다.
지금은 `RobotView`의 `speed = 클립길이/데이터길이`가 5배속을 걸어 억지로 맞추고 있다.
→ 변환은 **시간이 아니라 키 순서(n번째 키 = n번째 프레임)로** 읽는다.
→ 도트 직접 재생(B단계)으로 가면 이 불일치는 아예 사라진다.

**P5. 구간 경계에 걸친 박스는 자동 배정이 불가능하다.**
잽 도트B(4~7f)는 선딜과 활성에 걸쳐 있다.
→ 규칙: **Hurt·Push는 도트로, Hit은 활성 구간으로** 보낸다. 대부분 이걸로 맞는다.
→ 변환 후 **25개 전부 눈으로 검수.** 개수가 적어서 가능하다.

**P6. 에디터 미리보기는 "보정 없음" 기준이다.**
`ActionDataEditor`는 런타임 확정값을 모르므로 원본 기준으로만 그린다. 보정이 걸린 실제 모습은
게임 뷰 `BoxDrawer`(Keypad9)로만 확인된다.
→ 에디터에 "보정 미적용 기준" 문구를 띄운다. §4의 "거짓말하는 표시기"와 헷갈리지 않게.

### 🟡 런타임 수치 사고

**P7. 보정·반올림으로 활성이 0프레임이 되면 판정이 영영 안 켜진다.** 기술이 사라진 것처럼 보인다.
→ **활성은 최소 1프레임 강제.** 선딜·후딜은 0 허용(선딜 0 = 즉시 발동은 정상적인 기술).

**P8. 음수 프레임.** 원래 선딜 3인데 -4 보정이 걸리면 -1.
→ 확정 단계에서 `Max(0)` 클램프.

**P9. 도트 합 ≠ 구간 합.** 스케일·반올림 후 어긋나면 그림이 1프레임 남거나 모자란다.
→ 오차는 **그 구간의 마지막 도트가 흡수**한다. 규칙을 한 곳에 고정.

**P10. `FrameSpeedMultiplier`가 `Identity`에서 0이면 행동 시간이 0이 된다.**
→ 반드시 `1f`로 초기화. CSH가 `KnockbackMultiplier`에서 이미 겪고 주석을 남겨둔 함정이다.

**P11. 도트 층이 빈 에셋이 존재한다** (BackspinElbow는 클립 자체가 없음, Weaving·Guard는 박스 0개).
→ **도트 층이 비어 있으면 지금 방식(Animator 배속)으로 폴백.** 폴백이 없으면 그 기술이 화면에서 사라진다.

### 🟢 팀 경계 / 도구

**P12. `ActionState`의 `#region 최.추가`(`Resolved` / `ApplyHitBoxModifiers`)를 NYH가 옮기게 된다.**
계약(`Func<ActionData, ResolvedModifiers>`, `EffectInstance.Contribute`)은 **안 바뀐다.**
CSH 폴더 9개 파일에 `FrameBox`·`startFrame`·`GetActiveBoxes`·`StartupFrames` 참조는 **0건**이라
상희 님 쪽 수정 작업은 **지금 단계에서 0줄**이다.
→ 그래도 남의 코드 영역을 옮기는 것이므로 **사전 공유**.
→ 프레임 보정 기술을 실제로 만들 때만 `ResolvedModifiers`에 필드 4개 + `Contribute`에 4줄이 추가된다.
   그때 합의하면 되고, 지금 합의가 필요한 건 아니다.

**P13. B단계로 가면 `RobotView.AdvanceOneTick()`이 깨진다.**
지금은 `animator.Update(TICK)`인데 도트 직접 재생이면 도트 인덱스를 1 전진시켜야 한다.
안 고치면 Keypad8 프레임 스텝이 그림에 안 먹힌다 — 2026-09-21에 이미 한 번 겪은 문제와 같은 계열이다.

**P14. B단계로 가면 Animator Controller의 행동 스테이트가 실행 경로에서 빠진다.**
Idle / Walk / BackWalk / Hurt / Die는 계속 Animator를 쓴다.
→ 그래픽(심예성) 쪽에 클립 관리 방식 변경 공유 필요.

**P15. 보정 수치가 기획 미확정이라 검증할 실데이터가 없다.**
→ 테스트용 더미 `ActionModifierData` 1개(선딜 -2 / 활성 +2)로 수동 검증. FrameStepper로 프레임 대조.

**P16. §11 작업 순서상 StunSystem·RobotAssembler가 밀린다.**
`HitDetection`·`KnockbackSystem`은 `GetActiveBoxes()`만 보므로 **한 줄도 안 바뀐다.** KKH도 영향 없음.

## 5. 안전한 진행 순서

직렬화 값 소실(P1)을 막기 위해 아래 순서를 지킨다. 단계마다 커밋한다.

1. **신규 필드 추가** — `FrameBox`에 앵커 필드, `ActionData`에 도트 층. **구 필드는 그대로 둔다.**
2. **변환 도구** — 클립 드래그 → 도트 층 생성, 절대 프레임 박스 → 앵커 변환. 개수 불일치는 막는다(P3).
3. **변환 실행 + 눈 검수** — 에셋 9개, 박스 25개. Keypad8로 프레임 대조.
4. **런타임 전환** — `ResolvedAction` 도입, `Advance()`·`GetActiveBoxes()`가 확정값을 본다.
5. **구 필드 제거** — 4번이 검증된 뒤에만.

### 범위 선택

- **A (권장)** — 1~5단계까지. 그림은 지금 Animator 배속 유지.
  선딜·활성·속도 보정이 **판정 기준으로는 전부 정확하게** 동작한다.
  도트 층은 **스키마만 만들고 스프라이트는 비워둬도 된다** — 그래야 변환이 1회로 끝난다.
- **B** — A + `RobotView` 행동 도트 직접 재생. 그림까지 맞는다. P13·P14가 여기서 발생.

A 단계의 한계: 스프라이트를 꽂기 전까지 **활성 연장 보정이 들어오면 그림은 안 맞는다**
(배속으로는 특정 구간만 늘릴 수 없다). 판정·프레임은 정확하고, 도트를 꽂는 순간 그림도 맞는다.
