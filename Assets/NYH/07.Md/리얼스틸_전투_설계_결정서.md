## 1. 전투 방식이 무엇으로 결정됐나

### 물어본 것
기획서에 전투가 어떻게 되어 있는지, 앞으로 어떻게 만들지.

### 결론

| 항목 | 결정 |
|---|---|
| 전투 방식 | **실시간 액션 (입력 즉시 발동)**. 행동 큐 방식 폐기 |
| 공간 | **사이드뷰 평면**. 3×6 그리드 폐기 |
| 이동 | 좌우 2방향만 |
| 교전 | 근거리만 |
| 참고 | 스트리트 파이터 2~4 (격투 게임 구조를 그대로 차용) |

### 이게 왜 중요한가
그리드가 빠지면서 담당 3개(그리드/부위파괴/행동) 중 하나가 비었다.
그 자리를 **장비(파츠) 연결 — 로봇 조립**이 채운다. 실질적으로 그리드보다 중요한 자리다.

| 원래 담당 | 현재 담당 |
|---|---|
| ~~그리드~~ | **장비 연결 / 로봇 조립** (PartData → RuntimeRobot) |
| 부위파괴 | 그대로. 가드=팔 / 위닝=다리 / 치명타=머리 매핑이 더 깔끔해짐 |
| 행동 | 그대로 + 위닝 타이밍 판정 추가 |

### "격겜이라고 생각하고 짜면 된다"의 의미
격투 게임은 구조가 수십 년 다져진 장르라 고민할 게 적다. 핵심은 하나뿐:

> **모든 행동은 선딜 → 판정 → 후딜, 3구간 타임라인이다.**

잽도 위닝도 보스 기술도 전부 이 틀. 숫자만 다르다.
"위닝 타이밍이 빡빡하다"는 것도 별도 시스템이 아니라 **무적 프레임 숫자가 작다는 뜻일 뿐**이다.

## 2. 애니메이터용 기준 프레임

### 물어본 것
도트 애니메이터가 작업을 시작하려면 기준 프레임이 필요하다.

### 확정된 프레임 (60fps)

| 기술 | 선딜 | 판정 | 후딜 | 전체 | 기획서 근거 |
|---|---|---|---|---|---|
| 잽 | 4 | 2 | 6 | **12F** | "피해량만 있는 쿨타임 낮은 견제용" → 전체 최단 |
| 훅 | **3** | 3 | 14 | 20F | "선딜이 가장 짧은 기습 공격기" |
| 스트레이트 | 10 | 4 | 20 | 34F | "후딜 길고 타이밍 알기 쉬움" |
| 어퍼컷 | 13 | 3 | 18 | 34F | "선딜 길고 파괴력 있음" |
| 백스핀 엘보우 | **20** | 4 | 26 | **50F** | "선딜·후딜 제일 김, 피하기 쉬움" |
| 가드 | 2 | 유지 | 10 | — | "후딜은 남지만 확실히 막음" |
| 위닝 | 3 | **6(무적)** | 28 | 37F | "찰나의 타이밍, 후딜 매우 김" |

### 잽과 훅을 어떻게 구분했나
둘 다 "빠른 기술"이라 역할이 겹칠 위험이 있었다. 기획서 두 문장을 동시에 만족시키는 배치는 하나뿐이다.

- **잽** = *전체*가 짧다 (12F) → 연타로 계속 뿌리는 견제기
- **훅** = *선딜만* 짧다 (3F) → 발동이 안 보이는 기습기. 대신 후딜 14F

### 도트 작업량

| 기술 | 선딜 장수 | 판정 | 후딜 | 총 장수 | 임팩트 장 |
|---|---|---|---|---|---|
| 잽 | 2 | 1 | 2 | 5 | 3번째 |
| 훅 | 1 | 1 | 5 | 7 | 2번째 |
| 스트레이트 | 4 | 2 | 7 | 13 | 5번째 |
| 어퍼컷 | 5 | 1 | 6 | 12 | 6번째 |
| 백스핀 엘보우 | 7 | 2 | 9 | 18 | 8번째 |
| 위닝 | 1 | 2 | 10 | 13 | — |

**주요 7개 = 73장.** (장당 유지 3프레임 기준. 프레임표에서 조절 가능)
여기에 걷기 앞/뒤, 대기, 피격 약/강, 다운·기상, 경직, 가드 히트, KO가 추가된다.

### 애니메이터에게 반드시 전달할 것
- **피벗은 전 클립 '발밑 중앙' 통일** — 안 맞으면 공격할 때 캐릭터가 순간이동함
- **캔버스 크기도 전 클립 동일** — 다르면 판정 좌표가 전부 어긋남
- 프레임표의 숫자가 바뀌면 장수가 자동으로 바뀐다. "표 다시 봐"로 전달 끝

## 3. 이동·애니메이션·판정을 어떻게 구현할 것인가

### 물어본 것
2.5D에서 스프라이트를 움직이고, 차후 공격판정·피격판정을 어떻게 만들 것인가.

### 결론: Unity 콜라이더를 쓰지 않는다

`BoxCollider` + `OnTriggerEnter` 방식은 격투 게임에서 거의 반드시 터진다.

| 문제 | 내용 |
|---|---|
| 타이밍 불일치 | 물리 판정은 `FixedUpdate`(0.02초 ≈ 3프레임)에서 돈다. **활성 2프레임짜리 잽이 물리 스텝 사이로 통과한다** |
| 순서 제어 불가 | 동시에 서로 때렸을 때 누가 먼저인지를 엔진이 정한다. 이건 게임 규칙이라 우리가 정해야 한다 |
| 토글 불안정 | 프레임마다 콜라이더를 껐다 켜면 이벤트가 누락되거나 중복 발생한다 |

### 대신 쓰는 방식

판정을 오브젝트가 아니라 **데이터**로 들고, 매 프레임 직접 겹침을 계산한다.

```
매 프레임:
  1. 두 캐릭터의 상태를 1프레임 전진
  2. 각자 현재 프레임의 박스를 데이터에서 꺼냄
  3. AABB 겹침 검사  ← 부등호 4개
  4. 겹쳤으면 히트 처리
```

부수 효과로 얻는 것: 판정이 눈에 보이는 데이터라 디버그 그리기가 쉽고, 처리 순서를 우리가 정하고,
나중에 리플레이·롤백까지 열린다. 좌우로만 싸우므로 사실상 1차원이라 더 단순하다.

### 2.5D 스프라이트 처리
- 스프라이트는 3D 공간의 쿼드에 붙이고 카메라 정면 고정 → 좌우로만 움직이므로 빌보드 문제 없음
- 좌우 반전은 `localScale.x = -1`이 간단하지만 **판정 박스 좌표도 같이 뒤집어야 한다** (§5 함정 참조)
- 정렬은 Z축이 아니라 `sortingOrder` — 2.5D에서 Z 정렬은 카메라 각도 변화에 깨진다

### 애니메이션 속도 맞추기
**데이터가 진실이고 애니메이션이 따라온다.**

```
데이터: 잽 = 12프레임
   ↓
상태기계가 12프레임을 센다     ← 게임 규칙
   ↓
Animator에 speed = 클립길이/데이터길이를 넣어 맞춘다   ← 그림은 따라올 뿐
```

반대로 하면(애니메이션이 끝나면 상태 종료) 클립 하나만 교체돼도 밸런스가 통째로 틀어진다.
Animator Controller에 전이를 주렁주렁 다는 것도 피한다 — 격겜은 조건이 너무 많아 금방 스파게티가 된다.

## 4. 아키텍처 — 상속 대신 무엇을 쓸 것인가

### 물어본 것
"팔다리/행동마다 따로 스크립트를 만들고 플레이어 베이스가 상속받는 형식"이 어떤가.

### 결론: 상속은 쓰지 않는다

| 문제 | 내용 |
|---|---|
| 1 | **C#은 다중 상속이 안 된다.** 팔·다리·머리·행동을 동시에 상속할 방법이 없다 |
| 2 | **상속은 "~이다" 관계다.** 플레이어 is a 팔? 아니다. 플레이어가 팔을 *가지고* 있다 = 포함(has-a) |
| 3 | **클래스가 폭발한다.** 기본기 5 + 방어 2 + 스킬 4 = 11개. 보스 8명 × 3기술 = 24개 더. **총 35개 클래스**가 전부 같은 선딜/판정/후딜 코드를 복붙하게 된다 |
| 4 | **밸런스 수정이 코드 수정이 된다.** 엑셀에서 잽 후딜을 6→7로 바꿀 때마다 코드를 고쳐야 한다 |

### 대안: 3층 구조

```
1층 · 데이터 (ScriptableObject)   불변. 에셋으로 존재
     ActionData   PartData   CoreData   FrameBox
2층 · 런타임 상태 (순수 C# class)  가변. 전투 중에만 존재
     RuntimeRobot  RuntimePart  RuntimeCore  ActionState
3층 · 시스템 (MonoBehaviour)       규칙. 개수 고정
     ActionExecutor  HitDetection  DurabilitySystem
     KnockbackSystem StunSystem    RobotAssembler
```

**핵심 원칙: 기술이 35개가 되어도 클래스는 늘어나지 않는다. 에셋만 늘어난다.**

### 확장성이 어떻게 풀리는가

| 요구 | 작업량 |
|---|---|
| 파츠에 내구도·경직치·체력 추가 | `PartData`에 필드 하나 추가. 구조 그대로 |
| 스킬 추가 | `ActionData` 에셋 하나 생성 + 파츠에 연결. **코드 0줄** |
| 부위 파괴 시 스킬 잠금 | `RuntimeRobot`이 목록 갱신. 한 곳에서 끝 |
| 밸런스 조정 | 엑셀 → 에셋. 코드 안 건드림 |

### 상속/인터페이스를 쓰는 유일한 자리

플레이어와 적(AI)은 둘 다 로봇이고 대부분 같다. 차이는 **입력을 사람이 주냐 AI가 주냐**뿐이다.

```csharp
interface IInputSource            // 이것만 갈라진다
{
    ActionData GetDesiredAction();
    float      GetMoveInput();
}
class PlayerInputSource : IInputSource   // 키보드
class AIInputSource     : IInputSource   // 보스 패턴
```

로봇 본체는 하나. 입력만 바꿔 끼우면 플레이어도 되고 보스도 된다.
**"무엇이 다른지"만 갈라내는 것** — 이게 상속/인터페이스를 쓰는 옳은 기준이다.

## 5. 히트박스 표시 기능

### 물어본 것
격투 게임 프레임표처럼 히트박스/피격박스를 네모로 보여주는 기능을 만들 수 있나.

### 결론
만들 수 있는 정도가 아니라 **데이터 방식으로 짜면 자동으로 따라온다.**
콜라이더 방식이면 표시기를 따로 만들어야 하지만, 데이터 방식은 그릴 데이터가 이미 손에 있다.

### 박스는 3종류

| 종류 | 색 관례 | 역할 | 단위 |
|---|---|---|---|
| **히트박스** | 빨강 | 내 공격이 닿는 범위 | 활성 구간당 1개 |
| **허트박스** | 하늘 | 내가 맞는 범위 | **도트 1장당 1세트** |
| **푸시박스** | 초록 | 몸끼리 겹쳐 지나가지 못하게 하는 상자 | 액션당 1개 |

**푸시박스를 빼먹으면 두 로봇이 서로 통과한다.** 그리고 넉백이 실제로 미는 대상은 히트박스가 아니라 이 상자다.

허트박스는 **부위별로 쪼갠다.** 기획서의 "치명타 시 머리 내구도 감소"를 판정하려면
머리에 맞았는지 몸통에 맞았는지를 구분할 방법이 이것뿐이다.

### 데이터 형태

```csharp
public enum BoxType  { Hit, Hurt, Push }
public enum BodyPart { Head, LeftArm, RightArm, LeftLeg, RightLeg, Core }

[System.Serializable]
public struct FrameBox
{
    public BoxType  type;
    public BodyPart bodyPart;   // 허트박스에서 필수
    public Rect     rect;       // 피벗 기준 로컬 좌표
    public int      startFrame;
    public int      endFrame;
}
```

`rect`를 로컬 좌표로 두는 이유: 캐릭터가 움직여도 박스를 다시 만들 필요가 없고, 좌우 반전 처리가 한 곳으로 모인다.

### 구현 3단계

| 단계 | 내용 | 비용 |
|---|---|---|
| 1 | `OnDrawGizmos` — Scene 뷰 전용, 빌드에 안 들어감 | 30분 |
| 2 | `GL` 또는 반투명 쿼드로 Game 뷰에도 표시 + 토글 키 | 반나절 |
| 3 | **프레임 단위 정지·전진** (F2 정지 / F3 한 프레임) | 반나절 |

3단계가 진짜 무기다. 20프레임짜리 백스핀을 눈으로 볼 방법이 이것뿐이고,
**프레임표가 맞는지 검증할 유일한 수단**이다.

### 지켜야 할 규칙 하나

> **표시기가 읽는 데이터와 판정이 읽는 데이터가 같아야 한다.**

별도 `DebugBox` 리스트를 두면 **거짓말하는 표시기**가 된다.
화면엔 안 맞는데 맞고, 맞는데 안 맞는다. 도구를 못 믿게 되는 게 제일 악질이다.

```
                ┌── HitDetection (판정)
GetActiveBoxes ─┤
                └── BoxDrawer    (표시)
```

### 함정 — 좌우 반전

`localScale.x = -1`은 스프라이트만 뒤집고 박스 데이터는 안 건드린다.

```csharp
float worldX = facingRight ? pos.x + box.rect.x
                           : pos.x - box.rect.x - box.rect.width;
```

빼먹으면 **오른쪽 볼 때만 맞고 왼쪽 볼 땐 등 뒤를 때리는** 버그가 난다.
이 변환은 반드시 단일 지점에서만 수행한다. 흩어지면 한쪽을 빠뜨린다.

### 박스 좌표는 엑셀에 넣지 않는다

| 엑셀 | 유니티 |
|---|---|
| 프레임, 데미지, 스턴, 넉백, 내구도 | 박스 위치·크기 |
| 밸런스 숫자 | 공간 데이터 |
| 기획이 정함 | 스프라이트 보면서 맞춤 |

`x: 0.4, y: 1.2, w: 0.6, h: 0.3`을 타이핑해서 주먹 위치를 맞출 수는 없다.

### 만드는 순서

1. 상태기계 (잽 하나가 3구간으로 도는 것)
2. `OnDrawGizmos`로 박스 표시 — 판정 없이 네모만
3. 프레임 정지·전진 키 — 여기서 표 검증
4. **그 다음에** 겹침 판정

3번이 4번보다 먼저인 게 핵심이다. **판정을 만들기 전에 판정을 볼 수 있게 만든다.**

## 6. 세부 결정 3가지

### 6-1. 부위 파괴 시 "잽 못 씀" 판정은 어디서 하나

**`RuntimeRobot`이 사용 가능 목록을 보유한다.**

| 후보 | 판정 |
|---|---|
| `ActionData`가 스스로 판단 | ❌ 에셋은 불변이고 모든 로봇이 공유한다. "누구의" 왼팔인지 알 수 없다 |
| `ActionExecutor`가 실행 직전 검사 | ❌ 동작은 하지만 UI가 버튼을 회색 처리할 수 없고, AI가 못 쓰는 기술을 계속 고른다 |
| **`RuntimeRobot`이 목록 보유** | ⭕ 입력·UI·AI가 같은 목록 하나를 본다 |

```csharp
class RuntimeRobot
{
    List<ActionData> availableActions;
    void OnPartBroken(BodyPart p) => RebuildAvailableActions();   // 이벤트 시 1회
}
```

매 프레임 검사가 아니라 **부위 상태가 바뀌는 이벤트에서만 1회** 갱신한다.

### 6-2. 히트박스는 프레임별인가 구간별인가

**구간별. 단 셋을 다르게 다룬다.**

프레임별은 과하다. 근거는 프레임표에 있다 — 활성 구간이 최대 6프레임이고 그 구간의 도트가 1~2장뿐이다.

| 기술 | 판정 프레임 | 판정 구간 도트 장수 |
|---|---|---|
| 잽 | 2F | 1장 |
| 훅 | 3F | 1장 |
| 스트레이트 | 4F | 2장 |
| 백스핀 | 4F | 2장 |

그림이 1장인데 박스를 프레임마다 다르게 둘 이유가 없다.

**단, 허트박스만 도트 장 단위로 준다.** 팔을 뻗으면 맞는 범위도 같이 늘어나야 하기 때문이다.
백스핀 선딜 7장 내내 같은 허트박스면 이상해진다.
이건 "큰 기술일수록 리스크가 크다"를 만드는 격겜의 기본 장치이고, 너희 게임의 팔 내구도 시스템과도 직결된다.

### 6-3. `FrameBox`에 빠진 필드

**부위 태그 (`BodyPart`)** — 부위 파괴용으로 이미 쓰는 그 enum이다.

허트박스에만 의미가 있고 두 곳에서 쓰인다:
1. **치명타 판정** — 머리 허트박스에 맞았을 때만 머리 내구도 감소 (기획서 587행)
2. **부위 파괴 연출** — 파괴된 부위는 반투명 + **그 부위 허트박스도 제거** (기획서 582행)

2번이 은근히 중요하다. 왼팔이 날아갔으면 없는 팔을 때릴 수는 없다.

## 7. 기획서에서 발견한 문제 (이현민 팀장 전달용)

| # | 위치 | 문제 |
|---|---|---|
| 1 | 게임 개요 15~17행 | 아직 "4방향 이동 / 행동 큐 기반 전투"로 되어 있음. 시스템 섹션(실시간 사이드뷰)과 모순 |
| 2 | 785행 이하 | 구버전 1000.1v가 통째로 남아 있음. 그리드 전투·명령어 블록 방식이라 현행과 완전히 다름. 팀원이 보고 작업하면 사고 |
| 3 | 883~890행 | 역할 분담표도 구버전 — "적(AI) 윤호", "전투(그리드) 관현". 앞쪽 팀 명단과 다름 |
| 4 | 534행 외 | "위빙"과 "위닝" 표기가 섞여 있음. 하나로 통일 필요 |
| 5 | 512~524행 | "현재 플레이어가 공격을 할 수 있는 **슬롯**인지" — 슬롯은 행동 큐 시절의 잔재. 실시간에서는 "다른 행동 중인가 / 경직인가"로 바뀌어야 함 |
| 6 | 543~550행 | 잽과 훅이 둘 다 "빠른 기술"이라 역할이 겹칠 위험. 잽=전체 짧음 / 훅=선딜만 짧음으로 갈라뒀으니 확인 필요 |

### 프레임표 v2에서 v3로 뒤집힌 이유
v2는 SF6 프레임표에서 수치를 가져왔는데, 기획서 v1000.2의 `행동 설명`(525~554행)과 **정반대**였다.

| 기술 | 기획서 요구 | SF6 값 |
|---|---|---|
| 훅 | 선딜 가장 짧음, 피해 낮음 | 선딜 최장, 피해 높음 |
| 어퍼컷 | 선딜 김, 피해 높음, 사거리 짧음 | 선딜 최단, 피해 최저 |

애니메이터가 v2로 작업을 시작했으면 전부 다시 그려야 했다. **v3부터는 기획서가 유일한 근거다.**

## 8. 아직 안 정해진 것 — 채울 순서

| 순위 | 항목 | 비고 |
|---|---|---|
| 1 | 부위별 내구도 최대치 (머리/팔/다리) | 이게 없으면 내구도 감소량을 정할 수 없음 |
| 2 | 가드 시 팔 / 위닝 시 다리 / 치명타 시 머리 내구도 감소량 | |
| 3 | 넉백 4칸 (히트/가드 × 상대/자기) | 이게 없으면 콤보 길이 조절 불가 |
| 4 | 경직도 회복 속도 | 한계치 100, 지속 120F는 기획서 기준으로 채워둠 |
| 5 | 스킬 5~8번 (이름·프레임·데미지 전부) | |
| 6 | 필살기 — 경직 상태에서만 쓰는 기술 | 기획서에 수치 없음 |
| 7 | 파츠 등급별 파괴확률 | 기획서 478행 "미정" |
| 8 | 위닝 쿨타임 / 기상 프레임 / 교전 거리 / 치명타 조건 | |
| 9 | 애니메이션 클립 이름 | 그래픽 담당과 합의 |

### 넉백 값 잡을 때 요령
**잽 넉백은 아주 작게 잡을 것.** 잽으로 상대를 밀어낼 수 있으면
"잽만 쳐서 거리 벌리기"가 최적해가 되어 게임이 지루해진다. SF2도 약공격 넉백이 거의 없다.

## 9. 신뢰도 표시

| 항목 | 신뢰도 | 근거 |
|---|---|---|
| 아키텍처 (3층 구조, 포함 vs 상속) | **95%** | 일반적인 게임 아키텍처 원칙. 규모·요구사항에 부합 |
| 판정 방식 (콜라이더 배제, 데이터 AABB) | **95%** | 상용 격투 게임의 표준 방식. `FixedUpdate` 문제는 수치로 확인 가능 |
| 프레임 서열 (어느 기술이 빠르고 느린가) | **95%** | 기획서 `행동 설명` 서술에 직접 근거 |
| 프레임 절대값 (4F, 20F 등) | **60%** | SF2~4 관례 기반 추정. 서열은 맞지만 체감은 플레이해봐야 함 |
| 도트 장수 | **70%** | 장당 3프레임 가정. 애니메이터 스타일에 따라 달라질 수 있음 |
| 사용 부위 매핑 (잽=왼팔 등) | **50%** | 근거 없음. 애니메이션 나오면 맞춰야 함 |
| 다운 유발 매핑 (어퍼컷·백스핀) | **40%** | 큰 기술이라 다운으로 잡음. 기획서에 명시 없음 |
| 넉백·경직도 수치 | **0%** | 채우지 않음. 지어내면 밸런스가 통째로 틀어짐 |
