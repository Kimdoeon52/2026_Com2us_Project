### 문제 → 원인 → 해결

**1. ScriptableObject 원장 데이터를 런타임에서 직접 수정 시 에셋 오염 문제**
- 증상: 전투 중 피격이나 가드로 인해 파츠 내구도나 코어 체력을 깎을 때, SO 에셋 필드를 직접 건드리면 유니티 에디터 플레이 모드가 끝나도 수치가 원복되지 않고 디스크에 영구 변경될 위험이 있었음. 또한 동일한 파츠를 장착한 복수의 기체가 데이터를 공유하는 버그 발생 가능.
- 원인: ScriptableObject는 불변의 '마스터 템플릿(원장)'이지 런타임 개별 개체의 '상태 인스턴스'가 아님.
- 해결: 원장 SO는 오직 읽기 전용(Read-Only)으로만 취급하고, 전투 시작 시 원장의 수치를 복사해 개별 전투원마다 고유한 런타임 스냅샷(`CombatantSnapshot`)을 인스턴스화하여 데이터를 완전히 격리함.

**2. 다리 파손 시 위빙 실패 확률(50%) 및 팔 파손 시 가드 불가 판정의 위치 모호함**
- 증상: 기획서상 "양다리가 모두 파손되면 위빙 시 50% 확률로 실패"하고 "팔이 파손되면 가드 불가"인데, 이 판정을 액션 실행부(NYH)에서 할지 데이터 허브(KKH)에서 할지 경계가 불분명했음.
- 원인: 상태 검사와 확률 계산의 책임 분리가 명확하지 않았음.
- 해결: 상태의 '진실(True State)'은 `CombatantSnapshot`이 쥐고, NYH 파트가 행동 시작 전 질의할 수 있는 질의 메서드(`CanGuard()`, `CheckWeavingSuccess()`)를 스냅샷 및 데이터 허브에 배치하기로 계약 정리.

**2. BattleManager.OnBattleFinished 인스턴스 이벤트로 인한 컴파일 에러 (CS0120)**
- 증상: BattleResultUI에서 BattleManager.OnBattleFinished 구독 시 error CS0120: static이 아닌 필드, 메서드 또는 속성 'BattleManager.OnBattleFinished'에 개체 참조가 필요합니다 에러 발생.
- 원인: BattleManager.cs의 OnBattleFinished 이벤트가 public event 인스턴스 멤버로 선언되어 있어 정적 클래스명 참조 시 컴파일 거부됨.
- 해결: BattleManager.cs의 OnBattleFinished를 public static event로 선언 변경하여 싱글톤 인스턴스 라이프사이클이나 Awake 순서에 구애받지 않고 전역에서 안전하게 구독/발행할 수 있도록 표준화함.

**3. BattleResultUI 시작 시 SetActive(false)로 인한 OnDisable 및 이벤트 수신 차단**
- 증상: 보스 즉시 처치나 BattleManager.EndBattle 호출 시 콘솔에 디버그 로그는 정상 출력되나 결과 UI 오브젝트가 화면에 활성화되지 않음.
- 원인: BattleResultUI.cs의 Awake에서 esultPanelRoot.SetActive(false)를 호출할 때, esultPanelRoot가 자기 자신(gameObject)으로 지정되어 있으면 스크립트 컴포넌트 전체가 비활성화되면서 즉시 OnDisable()이 실행됨. 이로 인해 BattleManager.OnBattleFinished 이벤트 구독이 즉시 해제되어 전투 종료 이벤트를 영영 받지 못하는 유니티 라이프사이클 데드락 발생.
- 해결: Awake에서 GameObject 자체를 끄지 않고 CanvasGroup의 투명화(lpha = 0, locksRaycasts = false, interactable = false)로 화면에서만 숨기도록 개편(HidePanel()). 또한 ShowResult 시 비활성화된 오브젝트까지 탐색(FindObjectsInactive.Include)하여 강제로 깨우도록 이중 안전장치 탑재 완료.

### 설계 결정과 이유

- **마스터 DB(불변 원장)와 런타임 스냅샷(가변 상태)의 엄격한 분리**:
  - 데이터의 무결성을 보장하고, 추후 전투 재도전이나 테스트 반복 시 원본 에셋 재로드 비용 없이 스냅샷만 재생성하면 되도록 설계.
- **부위별(BodyPart) 독립 내구도 모델 채택**:
  - 기획서의 핵심 재미 요소인 "특정 부위 파괴를 통한 적의 행동 제약(팔 파괴=가드 불가, 다리 파괴=회피 실패)"을 완벽히 지원하기 위해 전체 HP 하나로 뭉뚱그리지 않고 5개 부위 내구도를 개별 딕셔너리로 관리.

### 문제 → 원인 → 해결

**1. 실행부(NYH)와 데이터 허브(KKH) 간 상호 참조로 인한 결합도 증가 위험**
- 증상: NYH의 `ActionExecutor`와 KKH의 `CombatCalculator`가 서로의 내부 구현을 직접 참조하게 되면, 한쪽의 코드 변경이 상대방 코드의 컴파일 에러로 이어질 위험이 컸음.
- 원인: 프레임 엔진과 수치 엔진 간의 명확한 완충 계층(Interface/Contract) 부재.
- 해결: `CombatDataHub`를 단일 진입점(Façade)으로 세우고, NYH의 `BodyPart` enum과 `ActionData` 필드(`Damage`, `IsGuardable`, `StaggerValue`)만을 '공통 계약(Contract)'으로 확정. 세부 계산 로직은 허브 안쪽으로 완벽히 은닉함.

**2. `ProcessHit` 호출 시 누가 누구를 때렸는지 식별하는 기준 문제**
- 증상: 유니티 GameObject나 Component 레퍼런스를 인자로 넘기면 씬 구조가 바뀌거나 프리팹 인스턴스화 시점에 참조가 깨지기 쉬움.
- 원인: 런타임 씬 오브젝트 레퍼런스에 대한 직접 의존.
- 해결: 모든 API를 불변의 고유 문자열 ID(`fighterId: "Player"`, `"Enemy"`)로 통일. 허브 내부에서 딕셔너리로 스냅샷을 조회하도록 추상화.

**2. BattleManager.OnBattleFinished 인스턴스 이벤트로 인한 컴파일 에러 (CS0120)**
- 증상: BattleResultUI에서 BattleManager.OnBattleFinished 구독 시 error CS0120: static이 아닌 필드, 메서드 또는 속성 'BattleManager.OnBattleFinished'에 개체 참조가 필요합니다 에러 발생.

**3. BattleResultUI 시작 시 SetActive(false)로 인한 OnDisable 및 이벤트 수신 차단**

### 문제 → 원인 → 해결

**1. 씬 로드 시점(Race Condition)으로 인한 HUD의 CombatDataHub 이벤트 구독 실패**
- 증상: 에디터에서 씬을 실행했을 때, HUD의 게이지와 수치 텍스트가 초기화되지 않고 멍하니 멈춰있었음.
- 원인: 유니티 `MonoBehaviour` 간의 `Awake`/`Start` 호출 순서는 보장되지 않는다. `FighterStatusHUD.Start()`가 실행되는 시점에 `CombatDataHub.Instance`가 아직 생성되지 않아 null이었고, 그 결과 이벤트 구독에 실패하여 이후 발생하는 모든 수치 변경 이벤트를 수신하지 못했음.
- 해결: `TrySubscribe()` 메서드를 분리하고, 실패 시 `WaitForHubAndSubscribeCoroutine()`을 가동하여 0.1초마다 허브 인스턴스를 확인한 뒤 인스턴스가 감지되는 즉시 안전하게 이벤트를 구독하고 `RefreshAllData()`로 초기 수치를 동기화하도록 구현.

**2. 문자열 `fighterId` 비교 시 공백이나 대소문자 불일치로 인한 이벤트 무시**
- 증상: 인스펙터에 `"Player "`처럼 실수로 공백이 들어가거나 호출부에서 소문자 `"player"`를 넘겼을 때, 수치 변경 이벤트가 발생해도 HUD가 반응하지 않음.
- 원인: C# 기본 `Equals` 또는 `==` 연산자는 공백과 대소문자가 정확히 일치해야만 `true`를 반환함.
- 해결: `fighterId.Trim().Equals(targetFighterID.Trim(), StringComparison.OrdinalIgnoreCase)`로 비교 로직을 정규화하여 작업자의 입력 실수에도 100% 견고하게 반응하도록 방어 코드를 작성함.

**3. 인스펙터 수동 연결 누락 시 NullReferenceException 및 작업 피로**
- 증상: 6개 위젯마다 슬라이더, 이미지, 텍스트 2개 등 총 24개의 인스펙터 슬롯을 일일이 수동 드래그 앤 드롭해야 했고, 하나라도 누락되면 런타임에 NRE가 발생함.
- 원인: 수작업 바인딩에 전적으로 의존하는 취약한 컴포넌트 설계.
- 해결: `Awake()`와 에디터 전용 `OnValidate()`에 Auto-Fallback 로직을 추가하여, 필드가 비어있으면 `GetComponentsInChildren`으로 오브젝트 이름의 키워드("Label", "HP", "Value", "Fill" 등)를 파싱해 자동으로 연결하도록 자동화함.

**4. 코어(Core) 체력과 파츠(Part) 내구도의 개념 혼선 및 이중 게이지 동기화**
- 증상: 기획서상 코어는 로봇의 '최종 생명력(HP)'이고 5개 파츠는 '방어/행동 내구도(Durability)'인데, UI 화면에는 가슴 중앙 위젯(CORE)과 화면 하단의 대형 총합 체력 슬라이더(`Total_HP`) 두 곳에 코어 상태가 동시에 표현되어야 했음.
- 원인: 코어를 단순한 또 하나의 파츠로 다룰 경우 하단 체력바와 가슴 위젯의 이벤트 경로가 분리되어 수치 불일치 버그가 생길 수 있었음.

- 원인: 초기 프로토타입 작성 시 타 파트 코드가 없던 상태에서 KKH 스크립트 상단에 `PartGrade`와 `BodyPart`를 임시로 선언해 두었던 코드가 잔류함.
- 해결: 고물상/코어(KDU) 파트의 `PartGrade`와 전투 행동(NYH) 파트의 `BodyPart`를 단일 진실 원천(Single Source of Truth)으로 확정하고, KKH `PartMasterData.cs` 상단의 중복 enum 선언을 완전히 삭제함.

**3. 1:1 대전 규칙 하에서 일반 적(로봇) 대전과 보스전의 스냅샷 구조적 모순 (보스전 편향 설계 결함)**
- 증상: 최근 보스 기믹(타이어 펑크/못판)을 설계서에 구체화하면서 `CombatDataHub`와 연산기가 오직 `BossSnapshot`만 바라보도록 고정되어, 경기장 상주 일반 적(NPC A·B·C)과의 1:1 대전을 처리할 공간과 API가 사라지는 모순 발생.
- 원인: 전장 링이 항상 1:1 대전이라는 대원칙 하에서 상대방(Opponent)의 성격(조립 로봇 vs 비대칭 보스)을 분기하지 않고 단일 보스전으로 성급하게 좁혀서 설계함.
- 해결: 대전 모드(`BattleMode.RobotVsRobot` / `BattleMode.RobotVsBoss`)를 명확히 분리함. 플레이어와 일반 적(NPC)은 기존 5파츠 조립 로봇 DTO인 `CombatantSnapshot`을 100% 공용하도록 확립하고, 보스는 `BossSnapshot`이 전담하도록 설계서를 v5.6으로 전면 개정함.

**2. BattleManager.OnBattleFinished 인스턴스 이벤트로 인한 컴파일 에러 (CS0120)**
- 증상: BattleResultUI에서 BattleManager.OnBattleFinished 구독 시 error CS0120: static이 아닌 필드, 메서드 또는 속성 'BattleManager.OnBattleFinished'에 개체 참조가 필요합니다 에러 발생.
- 원인: BattleManager.cs의 OnBattleFinished 이벤트가 public event 인스턴스 멤버로 선언되어 있어 정적 클래스명 참조 시 컴파일 거부됨.
- 해결: BattleManager.cs의 OnBattleFinished를 public static event로 선언 변경하여 싱글톤 인스턴스 라이프사이클이나 Awake 순서에 구애받지 않고 전역에서 안전하게 구독/발행할 수 있도록 표준화함.

**3. BattleResultUI 시작 시 SetActive(false)로 인한 OnDisable 및 이벤트 수신 차단**
- 증상: 보스 즉시 처치나 BattleManager.EndBattle 호출 시 콘솔에 디버그 로그는 정상 출력되나 결과 UI 오브젝트가 화면에 활성화되지 않음.
- 원인: BattleResultUI.cs의 Awake에서 esultPanelRoot.SetActive(false)를 호출할 때, esultPanelRoot가 자기 자신(gameObject)으로 지정되어 있으면 스크립트 컴포넌트 전체가 비활성화되면서 즉시 OnDisable()이 실행됨. 이로 인해 BattleManager.OnBattleFinished 이벤트 구독이 즉시 해제되어 전투 종료 이벤트를 영영 받지 못하는 유니티 라이프사이클 데드락 발생.
- 해결: Awake에서 GameObject 자체를 끄지 않고 CanvasGroup의 투명화(lpha = 0, locksRaycasts = false, interactable = false)로 화면에서만 숨기도록 개편(HidePanel()). 또한 ShowResult 시 비활성화된 오브젝트까지 탐색(FindObjectsInactive.Include)하여 강제로 깨우도록 이중 안전장치 탑재 완료.

### 설계 결정과 이유

- **1:1 대전 상대방에 따른 스냅샷 역할 분리 (`CombatantSnapshot` vs `BossSnapshot`)**:

- **보스 다변화 대비 범용 기믹 딕셔너리(`gimmickStates`) 아키텍처 채택**:
  - 특정 보스의 기믹(예: `tirePunctureCount`)을 스냅샷 필드에 하드코딩하면 추후 지역 2, 3 보스가 추가될 때마다 C# 스크립트를 계속 뜯어고쳐야 함.
  - 따라서 기믹을 `BossGimmickRuntimeState` 딕셔너리로 추상화하여, 향후 어떤 독특한 기믹을 가진 보스가 나와도 ScriptableObject 에셋 구성만으로 즉시 연동되는 고도의 확장성을 확보함.

  - 전조 시간, 쿨다운, 저지 필요 대미지, 속도 등 기획 수치가 빈번히 변경되는 보스 패턴을 하드코딩하지 않고 `BossPatternData` SO로 추출하여, 기획자가 에디터 인스펙터에서 즉시 밸런싱할 수 있도록 분리함.
- **CancellationToken 기반의 비동기 인터럽트(State Cancellation) 구조 채택**:
  - 2초 전조 시간 동안 대미지 누적으로 인한 강제 캔슬 및 상태 전이를 코루틴 대신 `CancellationTokenSource`로 안전하게 취소(Cancel) 처리하여, 상태 전환 시 잔류 비동기 타이머로 인한 예외나 오동작을 원천 차단함.
- **그로기 상태의 대미지 증폭 캡슐화**:
  - 기획서의 "못판 착지 시 4초 그로기 + 대미지 1.5배" 규칙을 외부 연산기나 피격자가 일일이 if문으로 검사하지 않고, `BossGroggyState.OnTakeDamage()` 내부에서 1.5배 배율(`damage * 1.5f`)을 계산하여 컨트롤러 체력에 반영하도록 상태 내부에 책임 캡슐화.

### 문제 → 원인 → 해결

**1. 보스가 맵 구석에 있을 때 360도 탄막의 비효율 및 회피 불합리성**
- 증상: 보스가 맵 좌/우 구석에 있을 때 360도로 탄막을 쏘면 천장 쪽 180도 탄환이 허공으로 낭비되고, 구석에 몰린 플레이어는 틈새로 회피할 공간이 부족해지는 레벨 디자인 결함 발생.
- 원인: 360도 전방위 탄막은 플레이어가 2D 평면에서 보스를 둘러싸는 탑뷰 게임에 적합하며, 사이드뷰 횡스크롤 고정 카메라 환경에는 맞지 않음.
- 해결: 보스와 플레이어의 중간 상단으로 타이어를 사출하여 발사점을 전장 중앙으로 유도하고, 플레이어가 위치한 지상 아래쪽 160도 반원 방향으로만 탄막을 쏟아붓도록 리팩토링하여 플레이어가 안전 틈새로 피할 수 있는 공평한 전투 환경 구축.

**2. 공중 사출 높이 과다 및 동시 탄막 발사로 인한 바이킹 연출 퇴색**
- 증상: 타이어가 공중 `3.5m`까지 너무 높이 떠올라 고정 카메라 화면 밖으로 벗어나 보이지 않았고, 10발이 한 번에 쏟아져 바이킹 특유의 왕복 스윙 느낌이 살지 않음.
- 원인: 탄막의 '바이킹' 기믹은 물리적 타이어의 이동보다 탄환 발사 궤적이 진자처럼 한쪽에서 반대쪽으로 순차적으로 훑고 다시 돌아오는 '스윕(Sweep)' 액션에 있었으며, 높이 설정값이 너무 컸음.
- 해결: 타이어 높이를 `1.7m`로 대폭 하향하고, 15도 간격(0번~12번)으로 좌➔우 훑고(정방향), 정점에서 0.2초 멈춘 뒤 우➔좌로 다시 훑는(역방향) 순차적 왕복 연사 시퀀스로 전면 개편함.

**3. 폴백 탄환 생성 시 `AddComponent<CircleCollider2D>` 실패 및 NullReferenceException**
- 증상: 탄환 프리팹 미할당 시 `FireSingleBullet` 249번째 줄에서 `NullReferenceException: Object reference not set to an instance of an object` 에러 발생.
- 원인: `GameObject.CreatePrimitive(PrimitiveType.Sphere)`로 생성된 3D 프리미티브의 `SphereCollider`는 `Destroy(col3d)` 호출 후에도 해당 프레임 끝까지 지연 파괴(Deferred)되므로 제거되지 않고 남아있음. 유니티 물리 엔진은 3D Collider가 붙어 있는 오브젝트에 2D Collider를 추가하는 것을 허용하지 않아 `AddComponent<CircleCollider2D>()`가 `null`을 반환했고, 뒤이은 `col2d.isTrigger` 접근 시 널 참조 예외 발생.
- 해결: 3D Primitive 대신 순수 2D GameObject(`new GameObject("BossFallbackBullet")`)를 생성하고, 16x16 원형 발광 텍스처를 런타임에 동적 생성(`GetOrCreateFallbackBulletSprite()`)하여 할당함으로써 3D 컴포넌트 충돌을 원천 차단하고 2D 물리 컴포넌트가 100% 안전하게 부착되도록 수정함.

**2. BattleManager.OnBattleFinished 인스턴스 이벤트로 인한 컴파일 에러 (CS0120)**
- 증상: BattleResultUI에서 BattleManager.OnBattleFinished 구독 시 error CS0120: static이 아닌 필드, 메서드 또는 속성 'BattleManager.OnBattleFinished'에 개체 참조가 필요합니다 에러 발생.
- 원인: BattleManager.cs의 OnBattleFinished 이벤트가 public event 인스턴스 멤버로 선언되어 있어 정적 클래스명 참조 시 컴파일 거부됨.
- 해결: BattleManager.cs의 OnBattleFinished를 public static event로 선언 변경하여 싱글톤 인스턴스 라이프사이클이나 Awake 순서에 구애받지 않고 전역에서 안전하게 구독/발행할 수 있도록 표준화함.

**3. BattleResultUI 시작 시 SetActive(false)로 인한 OnDisable 및 이벤트 수신 차단**
- 증상: 보스 즉시 처치나 BattleManager.EndBattle 호출 시 콘솔에 디버그 로그는 정상 출력되나 결과 UI 오브젝트가 화면에 활성화되지 않음.
- 원인: BattleResultUI.cs의 Awake에서 esultPanelRoot.SetActive(false)를 호출할 때, esultPanelRoot가 자기 자신(gameObject)으로 지정되어 있으면 스크립트 컴포넌트 전체가 비활성화되면서 즉시 OnDisable()이 실행됨. 이로 인해 BattleManager.OnBattleFinished 이벤트 구독이 즉시 해제되어 전투 종료 이벤트를 영영 받지 못하는 유니티 라이프사이클 데드락 발생.
- 해결: Awake에서 GameObject 자체를 끄지 않고 CanvasGroup의 투명화(lpha = 0, locksRaycasts = false, interactable = false)로 화면에서만 숨기도록 개편(HidePanel()). 또한 ShowResult 시 비활성화된 오브젝트까지 탐색(FindObjectsInactive.Include)하여 강제로 깨우도록 이중 안전장치 탑재 완료.

### 문제 → 원인 → 해결

**1. 초기 테스트 스크립트들의 `[RuntimeInitializeOnLoadMethod]`로 인한 씬 실행 간섭 및 키 충돌**
- 증상: 보스 테스트 씬(`Battle_Test_KKH`) 진입 시마다 초기 단위 테스트 로그가 콘솔 창에 대량 출력되고, `@HUD_InteractiveTester`가 자동 생성되어 숫자키 입력(1~5) 시 보스 테스트와 겹치거나 화면에 미사용 GUI 패널이 노출됨.
- 원인: 초기 백엔드 수치 연산 및 UI 갱신을 검증하기 위해 작성된 테스트 도구들이 씬 로드 시 자동 생성되도록 정적 훅이 걸려 있었음.
- 해결: 해당 스크립트들을 `99.Legacy` 폴더로 격리하고 자동 생성 어트리뷰트(`RuntimeInitializeOnLoadMethod`)를 주석 처리하여 불필요한 오브젝트 생성과 입력 간섭을 100% 원천 차단함.

**2. BattleManager.OnBattleFinished 인스턴스 이벤트로 인한 컴파일 에러 (CS0120)**
- 증상: BattleResultUI에서 BattleManager.OnBattleFinished 구독 시 error CS0120: static이 아닌 필드, 메서드 또는 속성 'BattleManager.OnBattleFinished'에 개체 참조가 필요합니다 에러 발생.
- 원인: BattleManager.cs의 OnBattleFinished 이벤트가 public event 인스턴스 멤버로 선언되어 있어 정적 클래스명 참조 시 컴파일 거부됨.
- 해결: BattleManager.cs의 OnBattleFinished를 public static event로 선언 변경하여 싱글톤 인스턴스 라이프사이클이나 Awake 순서에 구애받지 않고 전역에서 안전하게 구독/발행할 수 있도록 표준화함.

**3. BattleResultUI 시작 시 SetActive(false)로 인한 OnDisable 및 이벤트 수신 차단**
- 증상: 보스 즉시 처치나 BattleManager.EndBattle 호출 시 콘솔에 디버그 로그는 정상 출력되나 결과 UI 오브젝트가 화면에 활성화되지 않음.
- 원인: BattleResultUI.cs의 Awake에서 esultPanelRoot.SetActive(false)를 호출할 때, esultPanelRoot가 자기 자신(gameObject)으로 지정되어 있으면 스크립트 컴포넌트 전체가 비활성화되면서 즉시 OnDisable()이 실행됨. 이로 인해 BattleManager.OnBattleFinished 이벤트 구독이 즉시 해제되어 전투 종료 이벤트를 영영 받지 못하는 유니티 라이프사이클 데드락 발생.
- 해결: Awake에서 GameObject 자체를 끄지 않고 CanvasGroup의 투명화(lpha = 0, locksRaycasts = false, interactable = false)로 화면에서만 숨기도록 개편(HidePanel()). 또한 ShowResult 시 비활성화된 오브젝트까지 탐색(FindObjectsInactive.Include)하여 강제로 깨우도록 이중 안전장치 탑재 완료.

- 증상: 외부 `CombatDataHub.ProcessHit`에서 이미 방어력 감쇄 연산이 완료되어 전달될 때, 컨트롤러의 `TakeDamage`가 다시 방어력을 계산하면 대미지가 이중 감쇄되거나, 반대로 외부 연산만 수행하면 FSM의 300 DPS 저지 체크(`OnDamageTaken`) 및 기믹 내구도 차감이 누락되는 상호 배타성 문제 존재.
- 원인: 체력 차감 경로와 상태 머신/기믹 이벤트 브로드캐스팅 경로의 분리.
- 해결: `BossControllerBase.TakeDamage(int rawDamage, bool isAlreadyCalculated = false)`로 단일화하고 `NotifyDamageFromHub(int finalDamage)` 진입점을 제공. 외부에서 이미 연산된 피해는 추가 감쇄 없이 수용하되, 체력 차감 1회 + FSM 저지 게이지 누적 + 기믹 통보 + 페이즈 전환 검사 + 토벌 정산이 100% 한곳에서 처리되도록 SSOT 파이프라인 확립.

**3. 폐타이어 부위 파괴 시 스펙 약화 vs 스킬 영구 봉인 충돌**
- 증상: 기존 `BossAssetFactory`에 `TIRE_PART`의 `targetSkillIDToSeal = "PATTERN_JUMP_BARRAGE"`가 지정되어 있어, 타이어가 2회 펑크나면 바이킹 탄막이 영구 봉인되어 기획 의도인 "감속된 돌진 및 낮아진 탄막 높이의 약화된 패턴 유지"와 정면 충돌.
- 원인: 부위 파괴 시 스킬 봉인과 스펙 약화(Degradation) 메커니즘의 미분리.
- 해결: `BossPartGimmickBase`에서 `targetSkillIDToSeal`이 지정된 경우에만 스킬을 영구 봉인하도록 조건부 처리하고, `BossAssetFactory`에서 타이어 부위의 봉인 대상을 빈 문자열(`""`)로 보정. `JunkWheelerTirePartGimmick`이 펑크 2회 누적 시 돌진 기믹(50% 감속)과 탄막 기믹(30% 높이 감축)에 직접 디버프를 통보하도록 완벽히 정합성 보완.

  - 원인: 베이스 클래스(`BossPatternGimmickBase`)의 `OnTellStarted()`를 외부 접근을 위해 `public virtual`로 승격시켰으나, 해당 클래스를 상속한 NYH 보스 패턴 클래스들이 여전히 `protected override`로 남아있어 C# 오버라이드 접근 제어자 규칙 위반.
  - 해결: `KyodaiPalmPressPattern.cs` 및 `KyodaiMotionPattern.cs`의 `OnTellStarted()`를 `public override`로 일괄 수정하여 컴파일 에러 완전 해소.

### 설계 결정과 이유
- **코드 주도형 애니메이션 아키텍처 (Code-Driven Animation Architecture)**:
  - UniTask 기반 비동기 기믹 파이프라인(도약 ➔ 체공 ➔ 탄막 스윕 ➔ 착지)과 애니메이션 재생 시점이 코드 한 곳에서 결정되도록 캡슐화하여 유지보수성과 확장성을 극대화함.
