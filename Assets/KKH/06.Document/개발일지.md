전투 행동 및 판정 엔진 파트(NYH)와의 인터페이스 계약과 크래프팅/경제 등 타 파트와의 연동 기준을 다룬다.

### 문제 → 원인 → 해결

**1. ScriptableObject 원장 데이터를 런타임에서 직접 수정 시 에셋 오염 문제**
- 증상: 전투 중 피격이나 가드로 인해 파츠 내구도나 코어 체력을 깎을 때, SO 에셋 필드를 직접 건드리면 유니티 에디터 플레이 모드가 끝나도 수치가 원복되지 않고 디스크에 영구 변경될 위험이 있었음. 또한 동일한 파츠를 장착한 복수의 기체가 데이터를 공유하는 버그 발생 가능.
- 원인: ScriptableObject는 불변의 '마스터 템플릿(원장)'이지 런타임 개별 개체의 '상태 인스턴스'가 아님.
- 해결: 원장 SO는 오직 읽기 전용(Read-Only)으로만 취급하고, 전투 시작 시 원장의 수치를 복사해 개별 전투원마다 고유한 런타임 스냅샷(`CombatantSnapshot`)을 인스턴스화하여 데이터를 완전히 격리함.

**2. 다리 파손 시 위빙 실패 확률(50%) 및 팔 파손 시 가드 불가 판정의 위치 모호함**
- 증상: 기획서상 "양다리가 모두 파손되면 위빙 시 50% 확률로 실패"하고 "팔이 파손되면 가드 불가"인데, 이 판정을 액션 실행부(NYH)에서 할지 데이터 허브(KKH)에서 할지 경계가 불분명했음.
- 원인: 상태 검사와 확률 계산의 책임 분리가 명확하지 않았음.
- 해결: 상태의 '진실(True State)'은 `CombatantSnapshot`이 쥐고, NYH 파트가 행동 시작 전 질의할 수 있는 질의 메서드(`CanGuard()`, `CheckWeavingSuccess()`)를 스냅샷 및 데이터 허브에 배치하기로 계약 정리.

### 설계 결정과 이유

- **마스터 DB(불변 원장)와 런타임 스냅샷(가변 상태)의 엄격한 분리**:
  - 데이터의 무결성을 보장하고, 추후 전투 재도전이나 테스트 반복 시 원본 에셋 재로드 비용 없이 스냅샷만 재생성하면 되도록 설계.
- **부위별(BodyPart) 독립 내구도 모델 채택**:
  - 기획서의 핵심 재미 요소인 "특정 부위 파괴를 통한 적의 행동 제약(팔 파괴=가드 불가, 다리 파괴=회피 실패)"을 완벽히 지원하기 위해 전체 HP 하나로 뭉뚱그리지 않고 5개 부위 내구도를 개별 딕셔너리로 관리.

### 문제 → 원인 → 해결

**1. 실행부(NYH)와 데이터 허브(KKH) 간 상호 참조로 인한 결합도 증가 위험**
- 증상: NYH의 `ActionExecutor`와 KKH의 `CombatCalculator`가 서로의 내부 구현을 직접 참조하게 되면, 한쪽의 코드 변경이 상대방 코드의 컴파일 에러로 이어질 위험이 컸음.
- 원인: 프레임 엔진과 수치 엔진 간의 명확한 완충 계층(Interface/Contract) 부재.
- 해결: `CombatDataHub`를 단일 진입점(Façade)으로 세우고, NYH의 `BodyPart` enum과 `ActionData` 필드(`Damage`, `IsGuardable`, `StaggerValue`)만을 '공통 계약(Contract)'으로 확정. 세부 계산 로직은 허브 안쪽으로 완벽히 은닉함.

**2. `ProcessHit` 호출 시 누가 누구를 때렸는지 식별하는 기준 문제**
- 증상: 유니티 GameObject나 Component 레퍼런스를 인자로 넘기면 씬 구조가 바뀌거나 프리팹 인스턴스화 시점에 참조가 깨지기 쉬움.
- 원인: 런타임 씬 오브젝트 레퍼런스에 대한 직접 의존.
- 해결: 모든 API를 불변의 고유 문자열 ID(`fighterId: "Player"`, `"Enemy"`)로 통일. 허브 내부에서 딕셔너리로 스냅샷을 조회하도록 추상화.

### 설계 결정과 이유

- **`CombatCalculator`를 Unity 엔진 의존성이 없는 순수 C# 정적 클래스로 설계**:
  - `MonoBehaviour`를 상속받지 않고 유니티 API(`Time`, `GameObject`)를 배제하여, 씬 로드 없이도 C# 단위 테스트에서 즉시 수치 검증이 가능하게 만듦.
- **폴링(Polling) 대신 C# Action 이벤트 기반 알림 구조 채택**:
  - UI나 타 시스템이 매 프레임 `Update()`에서 체력을 확인하는 낭비를 없애고, 피격 등 수치 변화가 발생한 순간에만 이벤트로 브로드캐스팅하여 성능 최적화.

### 문제 → 원인 → 해결

**1. 씬 로드 시점(Race Condition)으로 인한 HUD의 CombatDataHub 이벤트 구독 실패**
- 증상: 에디터에서 씬을 실행했을 때, HUD의 게이지와 수치 텍스트가 초기화되지 않고 멍하니 멈춰있었음.
- 원인: 유니티 `MonoBehaviour` 간의 `Awake`/`Start` 호출 순서는 보장되지 않는다. `FighterStatusHUD.Start()`가 실행되는 시점에 `CombatDataHub.Instance`가 아직 생성되지 않아 null이었고, 그 결과 이벤트 구독에 실패하여 이후 발생하는 모든 수치 변경 이벤트를 수신하지 못했음.
- 해결: `TrySubscribe()` 메서드를 분리하고, 실패 시 `WaitForHubAndSubscribeCoroutine()`을 가동하여 0.1초마다 허브 인스턴스를 확인한 뒤 인스턴스가 감지되는 즉시 안전하게 이벤트를 구독하고 `RefreshAllData()`로 초기 수치를 동기화하도록 구현.

**2. 문자열 `fighterId` 비교 시 공백이나 대소문자 불일치로 인한 이벤트 무시**
- 증상: 인스펙터에 `"Player "`처럼 실수로 공백이 들어가거나 호출부에서 소문자 `"player"`를 넘겼을 때, 수치 변경 이벤트가 발생해도 HUD가 반응하지 않음.
- 원인: C# 기본 `Equals` 또는 `==` 연산자는 공백과 대소문자가 정확히 일치해야만 `true`를 반환함.
- 해결: `fighterId.Trim().Equals(targetFighterID.Trim(), StringComparison.OrdinalIgnoreCase)`로 비교 로직을 정규화하여 작업자의 입력 실수에도 100% 견고하게 반응하도록 방어 코드를 작성함.

**3. 인스펙터 수동 연결 누락 시 NullReferenceException 및 작업 피로**
- 증상: 6개 위젯마다 슬라이더, 이미지, 텍스트 2개 등 총 24개의 인스펙터 슬롯을 일일이 수동 드래그 앤 드롭해야 했고, 하나라도 누락되면 런타임에 NRE가 발생함.
- 원인: 수작업 바인딩에 전적으로 의존하는 취약한 컴포넌트 설계.
- 해결: `Awake()`와 에디터 전용 `OnValidate()`에 Auto-Fallback 로직을 추가하여, 필드가 비어있으면 `GetComponentsInChildren`으로 오브젝트 이름의 키워드("Label", "HP", "Value", "Fill" 등)를 파싱해 자동으로 연결하도록 자동화함.

**4. 코어(Core) 체력과 파츠(Part) 내구도의 개념 혼선 및 이중 게이지 동기화**
- 증상: 기획서상 코어는 로봇의 '최종 생명력(HP)'이고 5개 파츠는 '방어/행동 내구도(Durability)'인데, UI 화면에는 가슴 중앙 위젯(CORE)과 화면 하단의 대형 총합 체력 슬라이더(`Total_HP`) 두 곳에 코어 상태가 동시에 표현되어야 했음.
- 원인: 코어를 단순한 또 하나의 파츠로 다룰 경우 하단 체력바와 가슴 위젯의 이벤트 경로가 분리되어 수치 불일치 버그가 생길 수 있었음.
- 해결: `CombatDataHub`에서 코어 체력(`OnHpChanged`)과 파츠 내구도(`OnPartDurabilityChanged`)를 명확히 분리하되, `FighterStatusHUD`에서 `OnHpChanged` 수신 시 하단 대형 슬라이더와 가슴 중앙 CORE 위젯을 `UpdateCoreHpDisplay` 함수 하나로 묶어 동시에 갱신하도록 일원화함. 또한 `ApplyPartHit` API를 신설하여 부위 피격 시 파츠 내구도 손상과 본체 생명력 감소가 기획서 공식대로 동시 반영되도록 구현.

**5. 단위 테스트 연속 실행 시 잔류 스탯으로 인한 후속 검증 오류**
- 증상: `CombatDataHubTester`에서 여러 테스트 케이스를 순차 실행할 때, 앞선 테스트에서 깎인 체력/내구도가 남아있어 다음 테스트 결과가 실패로 판정됨.
- 원인: 인메모리 싱글톤 허브에 등록된 `CombatantSnapshot`이 테스트 간에 격리되지 않고 영구 변경 상태로 유지됨.
- 해결: 각 테스트 케이스 종료 후 참가자 데이터를 원장 SO 기준으로 100% 원복하는 Clean-up 로직을 추가하고, 허브에 `ResetFighter(fighterId)` API를 제공하여 테스트 간 격리성을 보장함.

### 설계 결정과 이유

전투 행동 엔진(NYH) 파트의 플레이어 실시간 액션 키 개편에 맞추어 키 충돌을 방지하기 위해 HUD 테스트 키 매핑을 조정했다. 프레임 타임라인 앵커링 개편 및 조작 체계 변경 과정에서 KKH 데이터 허브와의 정합성을 유지했다.

### 한 일

- **HUD 및 인터랙티브 테스터 단축키 충돌 조정 (`FighterStatusHUD.cs`, `HUDInteractiveTester.cs`)**:
  - NYH 파트가 플레이어 실시간 공격 및 회피 키를 전면 개편(A: 잽, Q: 스트레이트, S: 훅, W: 어퍼컷, T: 백스핀, Z: 가드, Space: 위빙 회피)함.
  - 기존 KKH HUD 테스터에서 코어 피격 단축키로 사용하던 `Space` 키가 NYH의 '위빙 회피' 키와 중복되어 동시 입력 간섭 발생.
  - 코어 피격 테스트 키를 `KeyCode.Space` $\rightarrow$ `KeyCode.LeftAlt`로 변경하여 전투 조작과 UI 테스트 단축키를 완전히 분리.
- **NYH 측 프레임 앵커(`FrameAnchor`/`ResolvedAction`) 구조 변경 사항 모니터링**:
  - NYH 파트에서 판정 박스의 절대 프레임 의존성을 제거하고 앵커링 구조로 전환하는 작업 진행 상황 공유 확인.
  - KKH의 `CombatCalculator`와 `CombatDataHub`의 수치 연산 파이프라인에는 영향을 주지 않는 구조임을 상호 검증.

### 문제 → 원인 → 해결

**1. 전투 씬에서 위빙 회피 시도 시 코어 피격 테스트 로직이 동시 발동하는 키 중복 간섭**
- 증상: 플레이어가 Space 키를 눌러 위빙을 시도할 때마다 HUD의 코어 체력이 -100씩 깎이는 현상 발생.
- 원인: NYH `PlayerInputSource`에서 Space를 위빙 키로 바인딩했는데, KKH `FighterStatusHUD`와 `HUDInteractiveTester`에서도 Space를 코어 직격 테스트 키로 리슨하고 있었음.
- 해결: 코어 피격 테스트 키를 `LeftAlt`로 신속히 재매핑하여 조작 충돌을 해소함.

### 설계 결정과 이유

- **독립 테스트 키와 인게임 액션 키의 엄격한 분리**:
  - 단위 테스트용 편의 기능이 실제 게임플레이 조작과 키를 공유하면 타 파트 기능 테스트 시 의도치 않은 데이터 오염을 유발하므로, 테스트 키는 인게임 조작에 쓰이지 않는 보조 키(`LeftAlt`, 숫자 패드 등)로 격리 배치.

### 다음에 할 일

1. 경제 파트(`GlobalGold`) 및 인벤토리 인터페이스 변경 사항 반영.
2. 새 전투 기획 방향성에 따른 수치 연산 파이프라인 대응 검토.

## 2026-09-29

### 요약
경제 파트(`GlobalGold`)의 인터페이스 변경 사항을 전투 정산기(`BattleSettlementProcessor`)에 반영하여 컴파일 에러 및 런타임 결함을 방지했다. 또한 팀에 배포된 `0929기획서`에 따른 전투 시스템 대규모 전환(PvE 보스전) 상황을 확인하고, KKH 데이터 허브의 기존 연동 계약 필드 보존 상태를 점검했다.

### 한 일

- **경제 시스템 연동 인터페이스 정합성 패치 (`BattleSettlementProcessor.cs`)**:
  - `GlobalGold.Instance`의 골드 입출금 메서드 시그니처가 캐릭터 ID(정수)에서 캐릭터 식별 문자열(`string`)로 변경됨.
  - 전투 승리 보상 및 패배 골드 정산 호출부를 `GlobalGold.Instance.GetGold("윤지우", result.GoldDelta)` 및 `UseGold("윤지우", ...)`로 업데이트하여 타 파트 경제 시스템과의 연동 정상화.
- **`0929기획서` 반영에 따른 전투 아키텍처 상호 영향도 분석**:
  - 새 기획서로 인해 기존 복싱 기반 1:1 대인 격투(잽/훅/어퍼컷/가드/경직도)가 폐기되고, 2.5D 실시간 액션 RPG 기반의 PvE 보스전(할로우나이트/스컬 스타일)으로 방향 전환됨.
  - NYH 파트에서 가드 기동 및 경직 시스템을 걷어내는 과정에서, KKH의 `CombatCalculator.EvaluateHit`이 참조하던 `ActionData.staggerValue`와 `isGuardable` 필드가 임시 유지되도록 계약 상태를 확인 (빌드 깨짐 방지).

### 문제 → 원인 → 해결

**1. 타 파트의 `GlobalGold` 시그니처 변경으로 인한 빌드 에러 위험**
- 증상: 경제 시스템 리팩토링 과정에서 `GetGold(int, int)` $\rightarrow$ `GetGold(string, int)`로 변경되어 전투 정산 모듈에서 타입 불일치 에러 발생.
- 원인: 타 파트(경제/인벤토리)의 메서드 인터페이스 변경 사항이 전투 정산부에 실시간으로 동기화되지 않음.
- 해결: `BattleSettlementProcessor` 내부의 골드 증감 호출부에 유효한 플레이어 식별자(`"윤지우"`)를 전달하도록 수정하여 의존성 해결.

### 설계 결정과 이유

- **파트 간 완충 계약(Contract)의 유효성 재확인**:
  - NYH 파트가 대규모 기획 변경으로 내부 액션 코드를 갈아엎는 도중에도, 사전에 `BattleManager_Architecture.md`와 `NYH_Integration_Guide.md`에서 확정해 둔 상호 참조 필드 규칙 덕분에 KKH 코드가 깨지지 않고 팀 빌드가 온전히 보존됨.

### 다음에 할 일
